Legacy socket balance initialization accepts both ordinary Interactive Brokers
account-summary tags and the ``$LEDGER-`` prefixed tags returned by some
``$LEDGER`` account-summary requests. LumiBot still selects the ``BASE``
currency rows for cash and net liquidation values.

Order ownership with multiple API clients
-----------------------------------------

Use a stable, distinct ``CLIENT_ID`` for each strategy process. The socket
adapter only imports and reconciles orders from that API client, and rejects
foreign-client cancellation. Numeric order IDs alone do not identify ownership.
Parsed orders retain ``broker_client_id``, ``broker_perm_id`` and
``broker_account``; known conflicting identities cannot overwrite local orders,
and duplicate cleanup touches only verified identity matches. Parsed options
and futures use the contract root symbol while retaining contract details such
as expiration, strike and right. Positions and balances still represent the
selected account, not isolated per-strategy holdings.

Each order-ID allocation asks IBKR for a fresh ``nextValidId`` and stays above
IDs already allocated by this connection. Remove downstream fixed-range
allocator patches to use this behavior. This is not a distributed reservation:
independent clients may still race.

BRACKET/OTO legs form one order graph: the parent and earlier children are
sent with ``transmit=False`` and the last child transmits the whole graph.
IBKR usually sends no callback for a staged leg, so the adapter sends every
leg of the graph without waiting on staged legs, then waits up to 10 seconds
for the graph as a whole. Only ``Submitted``, ``PreSubmitted`` or ``Filled``
confirms acceptance; ``PendingSubmit`` does not. Only documented
order-specific error codes can reject a pending submission; unrelated request
errors do not establish an order outcome.

A duplicate-ID rejection (103) is retried once with fresh numbers, and only
when no leg at or after the rejected leg can be live at IBKR. Tracked IDs and
parent/child links are updated together. Other rejections, a second 103 and
any uncertain graph fail without a retry. Staged legs are never cancelled.

Failed submissions raise ``IBKROrderSubmissionError`` (a ``RuntimeError``),
importable from ``lumibot.brokers.interactive_brokers``. It exposes
``outcome``, ``client_id``, ``account``, ``code``, ``error_message``,
``order_ids``, ``parent_order_id`` and per-leg ``legs``
(``IBKRSubmissionLeg`` with ``order_id``, ``parent_id``, ``transmit``,
``outcome``, ``code`` and ``message``). The outcome is:

* ``REJECTED``: IBKR positively rejected the graph and no leg is live.
* ``PARTIAL``: some legs were rejected while others were accepted; reconcile
  the accepted legs.
* ``UNKNOWN``: at least one leg was not confirmed within the timeout, including
  silent staged legs after the transmitting leg was sent and rejected. This is
  raised as ``IBKROrderSubmissionUnknown``, which is also a ``TimeoutError``.

For OCO orders the error covers the whole call: if the second peer fails after
the first was accepted, the outcome is ``PARTIAL`` (or ``UNKNOWN``) and
``legs`` includes the live first peer.

An unknown outcome is not a rejection and is never retried automatically:
reconcile orders at IBKR before submitting again. A rejected parent does not by
itself prove the children are absent; check the per-leg outcomes. A missing
order-ID reply before anything is sent still raises ``TimeoutError``. Public
strategy signatures are unchanged.

Native advanced orders
----------------------

The legacy TWS/IB Gateway socket adapter converts ``BRACKET`` and ``OTO``
orders with market or limit entries and one or two attached limit/stop exits
from ``child_orders`` (including exits generated by ``secondary_limit_price``
and ``secondary_stop_price``). Attached exits activate after the parent fills.
``OCO`` instead submits two independent limit/stop peers in one OCA group;
when either fills, the other is canceled. Cover/close-buy orders use IBKR
``BUY``; short/open-sell orders use ``SELL``.

Children must have the same asset, quantity, time-in-force, and good-till date
as the parent, with an opposing action for attached exits or matching action
for OCO peers. Invalid child counts, nested orders, and stop-limit/trailing
children are rejected rather than silently mapped to different order types.
Native stop-limit entry and simple orders require both ``stop_price`` and
``stop_limit_price``. Timezone-aware ``good_till_date`` values are sent in UTC;
naive datetimes retain Gateway-local wall-time formatting. Native child status
and fill callbacks update the corresponding tracked child orders.

Automatically generated children currently use ``DAY``. A non-``DAY`` parent
created with generated children is rejected before submission. For non-``DAY``
advanced orders, provide explicit children with matching durations. Conversion
tests are offline; live Gateway acceptance of non-``DAY`` orders and non-stock
instruments is not established.

For optional paper validation, use a controlled small whole-share stock
position: verify long and short market/limit BRACKET parent fills and either
exit, an OTO protective stop, both OCO exit paths with sibling cancellation,
then cancel an unfilled bracket parent and confirm attached children cancel.
Before finishing, reconcile the test symbol to a flat position and no open
test orders. Do not run this checklist against a live account.

Once installed, navigate in Trader Workstation to ``File -> Global Configuration -> API -> Settings`` The key settings required to trade using Lumibot are:

#. Enable ActiveX and Socket Clients
#. Disable Read-Only API
#. Socket port ``7496`` for live trading, ``7497`` for paper account trading.
    * NOTE: It is highly recommended to thoroughly test your algorithm in paper trading mode before trading live.
#. Master API Client ID: You can find in the Trader Workstation by going to ``File -> Global Configurations -> API -> Settings``, then looking for "Master API client ID". This can be any number you choose up to ``999``. You will use this in your configuration file to log in.

.. image:: interactive_brokers.png

Set up your credentials as follows in ``credentials.py``:

.. code-block:: python

    INTERACTIVE_BROKERS_CONFIG = {
        "SOCKET_PORT": 7497,
        "CLIENT_ID": "your Master API Client ID three digit number",
        "IP": "127.0.0.1",
    }

Set up your entry point file as above, except using Interactive Brokers. Here is an example of a completed file:

.. code-block:: python
    :emphasize-lines: 3,12

    from lumibot.traders import Trader
    # Import interactive brokers
    from lumibot.brokers import InteractiveBrokers
    from lumibot.strategies.examples import Strangle
    from credentials import INTERACTIVE_BROKERS_CONFIG


    trader = Trader()
    # Initialize interactive brokers
    interactive_brokers = InteractiveBrokers(INTERACTIVE_BROKERS_CONFIG)

    strategy = Strangle(broker=interactive_brokers)
    trader.add_strategy(strategy)
    trader.run_all()

You can also see the file simple_start_ib.py for a working bot here: https://github.com/Lumiwealth/lumibot/blob/master/getting_started/simple_start_ib.py
